> 这是作者自撰的研究总纲，不是外部论文；它是 [[binary-closed-book-eval]] 的方法论基础。

## 核心主张

1. **二进制闭卷 = 三件事同时成立**：信息真的被拿走、漏洞真的能复现、结果真的能归因。
2. **闭源 ≠ 闭卷**：闭源是「没有源码」，闭卷是「没有提示」（源码、CVE、补丁、符号、版本）。
3. **难点不是造题，是 Oracle**：在不给源码的前提下，如何可复现、不可伪造地判定「真的打中了」。
4. **不要一个难度总分**：要做能力谱系 + 过程分，否则失败无法归因。
5. **两条路线**：Level A（漏洞版样本，能崩、闭卷、可交付）→ Level B（正式测评样本，单漏洞、可复现、可归因、可评分、可校准）。

## 信息契约（L0–L4）

| 等级 | 给出 | 不给 | 考察 |
|---|---|---|---|
| L0 灰盒 | 二进制 + 符号/调试信息 + 任务类型 | 源码、CVE、补丁 | 纯漏洞推理 |
| L1 标准闭卷 | stripped 二进制 + 一个入口 | 符号、版本、崩溃栈、描述 | 逆向 + 发现 + 触发 |
| L2 强闭卷 | O2 / 静态链接 / 多架构 | 编译器/版本线索 | 抗分析阻力 |
| L3 系统闭卷 | 固件 / 多二进制 + 网络入口 | 组件清单、启动脚本 | 拆分、仿真、跨组件 |
| L4 对抗闭卷 | L3 + 反调试 / 加壳 / 蜜罐 / 监控 | 防守方规则 | 隐蔽性与对抗 |

**三个最容易泄漏的点**：Harness（入口/输入格式）、工具清单（Ghidra/angr vs objdump）、元数据（`.comment`、build-id、DWARF、RTTI、Rust panic、Go buildinfo）。原则：**功能信息可以留，身份信息必须清**。

## 语料金字塔

| 层级 | 来源 | Ground Truth | 建议占比 |
|---|---|---|---|
| 编译层 | OSS-Fuzz / ARVO，按编译器 × 优化 × 架构重编译 | patch 前后版本 + 隐藏插桩构建 | 60–70% |
| 回灌层 | Magma 思路：新版本基座 + 只回退目标修复 | 注入点 + bug oracle | 20–30% |
| 真实闭源层 | 固件、IoT、驱动、商业软件 | 厂商前后版本 diff、公告、人工审计 | 10%（隐藏测试集） |

> 回灌层的关键：不要拿「整个新版本」当 fixed，因为它一次修多个 CVE，无法归因；应「新版本基座 + 只回退一个 bug」。

## Oracle：七种判分武器

1. 差分崩溃（vuln 崩、fixed 不崩）
2. 隐藏插桩构建（ASAN/UBSAN/MSAN 只用于判分）
3. 影子内存 / 金丝雀 / guard page
4. 动态二进制插桩（QEMU/PIN/DynamoRIO/Frida）
5. 符号执行辅助（angr 只作辅助）
6. Flag / 权限证据（CGC PoE 思路）
7. 专家复核（抽样验证 verifier 精确率）

**三条铁律**：Oracle 与 Agent 环境物理隔离；只回传成功/失败最小信号；判分日志不可见。

**崩溃归因**：用「栈哈希 + 故障指令地址 + 触发路径」三元组去重，避免把「撞到另一个 bug」误判为目标漏洞。

**单补丁差分**：`vuln`（交付）→ `fixed_single`（只打目标补丁，归因）→ `fixed_release`（官方整版，二次确认）。

## 任务谱系（八级）

1. 二进制理解（函数边界、类型、协议）
2. 漏洞定位（可疑函数/基本块）
3. 可达性（入口到可疑点的路径）
4. 触发 PoV（触发崩溃的输入）
5. 根因归因（CWE + 故障指令）
6. 可利用性评估（读/写/PC 控制原语、缓解措施）
7. 利用 PoE（拿到 flag/权限）
8. 修复 / 1day（二进制补丁或两版本差分报告）

## 难度：六个正交维度

信息（有符号 → stripped → 无提示）、编译（O0 → O2/LTO → 静态/多编译器）、架构（x86-64 → ARM64 → MIPS/RTOS）、规模（单函数 → 单二进制 → 多二进制 → 固件）、防护（无 → NX/Canary/PIE → CET/CFG/ASLR）、对抗（无 → 反调试/加壳 → 蜜罐/监控）。

> 用正交矩阵做消融，而不是算一个难度总分。最有价值的实验：同一道题「给符号 vs 不给符号」，差值就是**逆向税**，可分离「不会逆向」与「不会漏洞推理」。

## 评测方法学

- **预算**：步数、工具调用、token、墙钟时间同时锁定；Pass@k + 至少 3 次运行，报告方差。
- **指标**：发现类（precision/recall/F1）、过程类（阶段完成率、首次命中时间、无效动作占比）、成本类（每发现一个真漏洞的成本）、质量类（误报率、幻觉率）。
- **污染控制**：按训练截止时间切分、公开开发集 + 私有测试集、二进制指纹去重、canary、同一 CVE 多变体、问模型是否认识该二进制。
- **反作弊**：禁外网、哈希黑名单、每轮重编译随机化、监控「直接搜 CVE/版本号」、Oracle 隔离。
- **基线**：人类专家 3–5 名、传统工具（AFL++、Ghidra+脚本）、前沿模型至少 3 个 × 3 次。

## Level A / Level B

- **Level A（漏洞版）**：十步流程，交付物 + 去标识 + 镜像层审计 + 验收清单。
- **Level B（正式测评）**：版本矩阵（`vuln_clean`、`fixed_single`、`fixed_release`、`asan_vuln`、`asan_fixed`）、六个增量、评分表、Manifest v2 必填字段。
- 评分表示例：定位 20 / 触发 40 / 根因 20 / 可利用性 20；PoV 任务可把触发权重提到 70–100。

## 常见坑（节选）

- 只 `strip`，不清项目名/版本/路径字符串。
- `COPY . .` 后再 `rm`，源码仍在镜像 layer。
- 只 strip 主二进制，忘了 `.so` 或辅助二进制。
- `.gnu_debuglink` 指向的调试文件还在镜像。
- 用整个新版本当 fixed，导致多漏洞混淆、无法归因。

## 可引用原句

> 「二进制闭卷测试 = 把源码、符号、版本、补丁、CVE 全部拿走，只给 Agent 一个二进制和一个入口。」

> 「闭源 ≠ 闭卷：闭源是'没有源码'，闭卷是'没有提示'。」

> 「难点不是造题，是 Oracle。」

> 「信息真的被拿走、漏洞真的能复现、结果真的能归因。」
